# compact-cache 设计说明

`compact-cache.ts` 替换 `/compact` 生成摘要的方式：把"停止工作、输出检查点"的指令追加到当前上下文末尾，作为最后一条 user 消息，复用上一次真实请求写入的 KV 前缀缓存。无法命中时退回 pi 原生压缩。切点、落盘、投影重建、TUI 与排队消息全部沿用 pi。

本文记录设计意图、判断依据和实测发现。具体实现以代码为准，这里不重复。实测集中在 deepseek-flash；Anthropic、gpt 中转和本地模型的 append 路径只有历史请求统计，没有专门实测。

旧版文档（含逐行源码引用、分阶段计划、逐轮改动记录）已被移入回收站（`~/.local/share/Trash/files/compact-cache_design.old.md`），需要查原始证据时从那里取。

---

## 1. 问题

pi 原生压缩是整套流程里最贵的一次请求。它强制 `cacheRetention: "none"` 并换新 sessionId，输入是被丢弃部分序列化后的纯文本，不命中任何缓存。

按单位 C（整段上下文全价输入的成本）估算：

| 路径 | 成本 |
| --- | --- |
| native | 约 0.5C |
| append 命中 | 约 0.1C（DeepSeek 缓存价约为输入价的 1/10） |
| append 未命中 | 约 1.0C |

`p × 0.1 + (1 − p) × 1.0 < 0.5` 得 `p > 0.56`。门限内命中概率超过六成，append 就比 native 便宜，所以 TTL 门限宜宽不宜窄：偏宽只损失少量差价，偏窄会放弃本可省下的费用。

native 的 0.5C 是估算值。旧文档里 native 输入占上下文的比例有两组数字（15–43% 与 39–58%），口径没有统一，实际比例随保留区大小而变。

## 2. 核心思路

### 2.1 为什么必须发全量上下文

缓存断点打在最后一条消息上。只发到切点为止的短前缀，等于依赖几分钟甚至几小时前写入的缓存，大概率已过期。发全量才能命中上一次请求刚写入的断点。

代价是输入量为 native 的 2.3–6.6 倍。命中时便宜 2–3 倍，未命中时贵 3–8 倍。

### 2.2 为什么回放快照，不重建请求

最初的方案是请求头哈希加自行重建请求，评审后被否决，原因有两层：

- 哈希只能证明"没变"，不能证明重建正确。
- 重建所需的信息，扩展在钩子里拿不到：
  - 系统提示：forced prompt 在 run 结束时被清除，钩子里的 `getSystemPrompt()` 只剩底稿。
  - 工具描述：会被 loadout 改写，`getAllTools` 看到的是改写前的。
  - 消息序列：经过 `buildSessionProjection`、`transformContext` 链、`convertToLlm` 与 `normalizeContext` 三层投影，`context_edit` 还会追溯改写更早的消息。

任何自行重建的方案都会静默偏差，后果是缓存全部失效而不报错。

采用的做法：平时把每次真实请求的完整 payload 存成快照。压缩时自己发请求，在 payload 生成后的回调里把快照的消息序列与新请求逐条比对，完全相等才放行，并把整份 payload 换成快照的，只保留新增的尾部。这一步同时承担门控、构造和最终校验，哈希可以整个删除。

契约：快照只用于回放，不用于重建。任何"从快照读一个字段再自己拼请求"的写法都是错的。

### 2.3 比对规则的取舍

- 在 payload 层比，不在 AgentMessage 层比，因为 transform 之后的内容才是真正发出去的。
- 比对时忽略所有 `cache_control`，并将消息 `content` 的字符串与仅含一个纯文本块的数组视为等价；不归一化工具参数，也不忽略文本块的额外字段。验证通过后保留快照原始前缀，只追加新尾部。
- openai-completions 把 system 放在 `messages[0]`，Anthropic 的 system 是顶层字段。比对时排除开头的 system/developer 消息，回放时用快照里的那条。
- 输出上限（`max_tokens` 等）不属于缓存前缀，永远取新请求。这条来自一个实际故障：pi 的缓存预热请求带 `maxTokens: 1`，openai-responses 适配器会把它抬成 16；如果守卫只认 1，预热请求会被当成快照，之后摘要继承 16 的上限而 `stop=length`。预热在本机从未运行（`models.json` 没声明 `promptCache`，`cost` 全为 0 使预热收益恒为 0），所以问题是读代码时发现的，没有在生产中出现。
- 显式指定思考档位或会话档位变化时，非结构参数整体取新请求，清除新请求已省略的旧参数，避免关闭思考后残留 `reasoning_effort`。否则沿用快照参数；`messages/input/tools/system/instructions` 始终取快照前缀。

## 3. pi 内部机制中影响设计的几点

- 压缩有三个入口：manual、threshold、overflow。overflow 时上下文已超窗，append 必然失败，必须走 native。threshold 路径上 `cancel` 之后请求照常发出，可能溢出，所以自动路径从不 cancel。
- 钩子返回完整 `compaction` 对象即可替代内置生成。
- `fromHook: true` 的条目不会被 pi 累积 `<read-files>` / `<modified-files>`。因此扩展产出的条目之后，pi 自己的压缩不会继承这份清单，扩展自己从上一条 compaction 的 `details` 合并。这也是 native 路径也由扩展调 `compact()`、而不是交回 pi 的原因之一。
- 扩展自己通过 `modelRegistry.streamSimple` 发的请求不经过 `before_provider_request` / `before_provider_headers`。`pi-cache-optimizer` 注入的 `prompt_cache_key`、剥掉的 `prompt_cache_retention` 都不会作用于这类请求。快照回放是唯一能让这类请求与会话请求一致的办法。
- `session_compact` 之后紧接着的 `compaction_end` 会清空聊天容器并从会话条目重建，之前 `notify` 出来的统计行随之消失（实测）。统计信息改放 widget，它不在聊天容器里。
- 统计信息不写进 summary（会进入上下文，破坏刚重建的前缀），也不用 `pi.sendMessage`（custom content 会进模型上下文）。

## 4. 门控

按优先级，第一条命中即走 native：

| 条件 | 说明 |
| --- | --- |
| overflow | 见第 3 节 |
| `-nc` | 用户指定 |
| `--model` 与当前不同 | 前缀按模型隔离，换模型必然不命中；同时带 `-c` 则提示矛盾 |
| 无快照（内存与磁盘都没有） | 无从回放 |
| 窗口余量 < 32k | 硬约束，`-c` 也不能越过 |
| 闲置时间 ≥ TTL 门限 | 带 `-c` 时只告警，照常 append |

几个判断：

- `-c` 只覆盖 TTL 这个猜测，不覆盖余量。早先 `-c` 越过 TTL 时也跳过了余量检查，会发出必然超窗、按全价计费的请求，已改为余量先于 TTL 判断。
- 思考档位不是门控条件。实测 low 与 high 之间切换仍有 99.7% 命中，档位变化只是让请求参数取自新 payload。早先的 `thinking-changed` 门槛会让 `-c` 永久失效，已删除。
- 前缀比对不在这张表里。它在 `onPayload` 内执行，比所有门控严格，是最后一道检查。
- 门控是纯函数，各分支的优先级由自检覆盖。

## 5. 快照

### 5.1 何时记

只有收到 200 的请求才算数。4xx/5xx 的请求没有写过缓存，若作为快照会通过 TTL 门控而服务器端什么都没有。流程是请求时先放入候选，`after_provider_response` 收到 200 才提交。

过滤掉不能作基准的请求：预热请求（输出上限 ≤ 16）和 pi 自己的摘要请求（system 含 "context summarization assistant"）。

### 5.2 何时落盘、存什么

内存里存引用，在 `agent_settled` / `session_shutdown` 时落盘。早先每次请求同步 `JSON.stringify` 约 1 MB payload，会拖慢每一次请求；丢失最后一轮只多一次 native 回落，代价小。

落盘位置 `~/.pi/agent/compact-cache/`，文件名由 `sessionId` 与模型拼成。只存 `{at, model, thinking, payload}`，**不存请求头**，因此内容与会话 jsonl 等价，不含凭据。超过 32M 字符不存，7 天未动的文件在会话启动时清理。

落盘的原因是一次实测事故：用户在 33 小时空白后 `/compact -c` 走了 native，因为恢复会话后内存快照为空。落盘后，新进程 resume 立刻 `-c` 实测命中 99.3%。

代价：磁盘快照没有请求头，路由型 provider 是否依赖回放的请求头，尚未验证。

### 5.3 不做主动失效

早先在 `session_tree`、`model_select`、`session_compact` 时清空快照。现在不清：快照按 `sessionId|模型` 分键，`replay` 的前缀比对会拒绝任何不是前缀的请求，过期快照只会降级，不会出错。

### 5.4 加载顺序约束

快照是引用保存的，所以本扩展的 `before_provider_request` 必须排在所有会改写 payload 的扩展之后。`pi-cache-optimizer` 返回副本而不是原地修改，更需要排在它后面。

实际加载顺序（读 `package-manager.resolve()` 确认）：`settings.packages`（项目在前、全局在后）、`settings.extensions` 显式条目、自动扫描 `~/.pi/agent/extensions/`、builtin。本扩展放在 `extensions/` 目录下，排在所有 packages 之后，满足约束。

顺序错了的表现是统计行报 MISS。曾经设计过运行时自检（快照里是否仍有 `prompt_cache_retention`），实测推翻：optimizer 对 deepseek 保留该字段，存在它不能证明顺序错，自检会错误地禁用整个 append 分支，已删除。

## 6. 降级链

append 失败（任何原因）和 `-nc` 都进入 native。native 不再交回 pi 内置压缩，最后一档失败就 `cancel`。

### 为什么不保留 pi 内置路径

读 `agent-session.js` 的 `_runDefaultCompaction`：它调的和扩展是同一个 `compact()`，同样的序列化、同样的 system prompt、同样的失败判据（出错、`length`）。它比扩展多出来的只有三样：虚拟模型路由、pi 的重试设置、取不到鉴权时仍发请求。

按失败原因看，内置路径解决不了扩展解决不了的问题：

| 失败原因 | 内置路径 |
| --- | --- |
| 摘要模型不可用或鉴权失败 | 用会话当前模型，扩展回退到当前模型即可覆盖 |
| 临时网络或服务错误 | 重试设置可能有帮助，扩展自己重试一次即可 |
| 输入超出窗口 | 没有任何缩减手段，同样溢出 |
| 输出被截断 | 同样抛错 |

唯一的实质差别是虚拟模型路由。`models.json` 与 `settings.json` 里没有虚拟模型（只查了这两个文件）。内置路径也不能保证成功，所以去掉。

代价：overflow 触发的压缩全部失败时，该回合直接失败。内置路径在这种情况下大概率同样失败，这一条是读源码的推断，没有实测。

另一个附带后果：交回 pi 会清空扩展累积的文件清单（第 3 节），去掉之后这一风险也没有了。

### 两次尝试

1. 配置的摘要模型和档位（`-m` / `-e` 优先），pi 默认序列化：丢思考块，工具结果截断到 2000 字符。
2. 会话当前的模型和档位，先对输入做更激进的截断再重试。

第 2 次截断的对象：

- 工具结果与 bash 输出：超过 500 字符的截到 500，并标明截掉的字符数。
- 工具调用的参数：同样超过 500 的截到 500。pi 的序列化只截工具结果，工具调用参数是原样写出的，写文件、编辑文件时参数里整段内容都会进入摘要请求。这一条不在最初的设想里，是读 `serializeConversation` 时发现的。
- 用户消息与 assistant 文本不动。

两次尝试用同一个 `compact()` 和同一份文件清单合并，第 2 次成功时统计 tag 追加 `|trimmed`。

取舍：

- 第 2 次是否真的更容易成功，取决于第 1 次的失败原因。模型不可用时，换当前模型就够了，截断是多余的；输入过长时，截断才起作用。目前不区分原因，两件事合在一档里，实现最简单，代价是第 2 次的摘要可能比必要的更粗。
- 截断后摘要无法引用被截掉的工具输出细节，质量下降且不报错，属于第 11 节第 3 条的同类风险。`|trimmed` 标记是唯一提示。
- 原先在发请求前用 `tokensBefore + 32k > 摘要模型窗口` 提前放弃，已删除：native 实际发送的是序列化后的被丢弃部分，远小于 `tokensBefore`，那个检查对小窗口模型过于保守。窗口放不下现在直接表现为请求报错，进入第 2 次尝试。

### 其他细节

- `event.signal` 已中断时不再发请求。
- append 单次尝试，不重试：重试叠加失败成本，而降级本身可靠。
- 判失败的条件与措辞无关：请求出错、输出被截断（`length`）、含工具调用、缺少固定的第一节标题。半截摘要不允许落盘。
- native 两次尝试不传 pi 的重试设置，也不自己重试同一参数。第 2 次尝试本身就是一次重试。
- 失败原因写入统计 tag：`native(no-snapshot)`、`native(ttl)`、`native(-nc)`；两次都失败追加 `|failed`，日志里的 `error` 字段记录最后一次错误，同时弹出错误通知。

### 原生摘要的模型与档位

native 是全价无缓存请求，指向便宜模型能省掉这一次。文件顶部两个常量 `NATIVE_SUMMARY_MODEL` 与 `NATIVE_SUMMARY_EFFORT` 控制它，都留空则沿用当前会话。

- 在 `session_start` 时匹配并缓存一次，配错当场报错，而不是等第一次压缩才发现；报错后退回当前模型与当前档位，压缩不受影响。
- 常量只是默认值，`--model` / `--effort` 是显式指令，优先于配置。
- 未配置模型时不缓存会话开始时的模型，否则 `/model` 切换后会钉在旧模型上。
- 档位在调用点按最终模型再校验一次，不支持则丢弃。
- 统计行报告的是 `compact()` 实际收到的参数；第 2 次尝试时报会话当前模型与档位。

### 档位校验

pi 的 `clampThinkingLevel` 会把未知档位静默降为 `off`，等于悄悄关掉思考。所以 `--effort` 在发请求前校验：先看是否在 pi 的档位词表内，再看该模型是否支持。支持判断镜像 pi 未导出的 `getSupportedThinkingLevels`。本机 deepseek 只有 `off / low / high / max`。overflow 触发的压缩跳过校验，因为 cancel 会让上下文继续超窗。

## 7. 摘要提示词

写进提示词的要点：

- 顺序：先硬性要求立刻停止当前工作、不调用工具，再给保留边界，最后才是输出格式与篇幅。格式放最后，因为模型必须严格照做，离生成位置越近越可靠。
- 保留边界不能靠位置：模型数不准消息条数，更数不准 token。做法是从保留区第一条消息摘一段逐字原文当锚点（切点永远不落在工具结果上，所以那条消息一定有文本或可用工具名）。锚点要在整个上下文里唯一，不唯一就加长或续拼下一行，仍不唯一则声明"全部内容都要压缩"。
- `## Goal` 起的小节标题固定，后处理靠它截断前言和代码围栏，接受 `#`~`###` 与 `**Goal**` 变体，避免模型换个标题层级就降级重付。
- 提示词里的篇幅目标（8k，不超过 12k）只让输出变短，不降低输入成本：保留区仍在请求里，模型仍会读。

实测摘要输出 2,920 / 5,939 / 8,889 / 9,943 / 9,749 token，与 `tokensBefore` 无关（365k 那次写了 9.9k，592k 那次只写 5.9k），所以否定了"按被丢弃量取百分比"的预算公式。

append 请求的输出上限固定为 `min(32768, model.maxTokens)`。不设的话适配器退回模型上限（deepseek 384k、claude 128k），加上接近窗口的输入会超窗。32768 与余量下限相等，保证通过余量检查就写得完。

`### Direction` 小节不能当作"用了我们的提示词"的判据：上下文里已有带该小节的旧摘要时，原生摘要也会模仿格式。可靠判据是请求总量是否约等于上下文总量。

## 8. 文件清单

pi 把读写过的文件清单存在 compaction 条目的 `details` 里。扩展产出的条目是 `fromHook`，pi 不会继承上一条的清单，所以扩展自己从分支里读上一条 compaction 的 details，与本次 `fileOps` 合并（被修改的文件从读取列表中剔除）。`computeFileLists` 与 `formatFileOperations` 未从包里导出，扩展自己实现，标签与 pi 保持一致，之后的原生压缩仍能解析。

## 9. 参数与取值

| 项 | 值 | 依据 |
| --- | --- | --- |
| `reserveTokens` | 1M 窗口 65536；本地模型在 settings 里按窗口单独覆盖（gemma 131k 为 36864，qwen 262k 为 49152） | 见下 |
| `keepRecentTokens` | 20000（pi 默认） | 压缩后的最小上下文占周期的 12–20% |
| 余量下限 | 32768 | 摘要 12k + 思考 16k + 余量 |
| 安全垫 | 4096 | 与 pi 的 `CONTEXT_SAFETY_TOKENS` 对齐 |
| 命中判定 | ≥ 0.75 命中，≤ 0.25 未命中，中间不判 | 全未命中时仍有 0.3–5% 读数 |
| TTL 门限 | TTL − 5min，TTL ≤ 5min 时不再减 | 覆盖请求时刻与写入时刻的偏差 |

### 为什么提高 `reserveTokens`

pi 默认 16384。阈值触发点的余量是 `reserveTokens − 4096`，只有 12288，永远够不到 32768 的下限，自动压缩会在余量门上一律降级。提到 65536 后余量 61440，全部通过。

代价：

- 阈值触发点提前约 49k token，1M 窗口下可用上下文少 6.5%。
- 压缩更频繁；append 未命中时 1.0C 高于 native 的约 0.5C。TTL 硬门控用来限制"闲置过久缓存必然已过期"的那部分风险。

收益：每次自动压缩从约 0.4–0.58C 降到约 0.1C。

本地模型按窗口取值：131k 窗口取 36864，刚好等于 32768 + 4096，是 append 能通过余量检查的最小值。更小的保留区会让该模型的自动压缩一律走 native。保留区按窗口分级，不按 provider 分；早先给本地模型统一压回 16384 是"本地推理没有缓存费用"的判断，副作用是小窗口模型也套用大模型的比例。

另有一个未经证实的推测：上下文接近窗口上限时模型注意力可能漂移，更早压缩可能对质量有帮助。没有对照实验，只作附带理由。

### TTL 取值

| provider | TTL | 依据 |
| --- | --- | --- |
| 本地（回环地址、provider 名含 `local`、或模型 id 含 `gguf` / `nvfp4` / `int4` / `fp8` / `bf16`） | 1h | 本地进程自己决定淘汰，无官方口径；原先设为永不过期，现改为 1h |
| deepseek | 3d | 官方口径 agent 缓存 3 天、聊天 7 天，负载大时动态清理；快照首次回放实测 51.10h / 65.94h / 69.10h 后仍分别命中 99.856% / 99.788% / 99.555%，不保证固定保留 72h |
| claude / `anthropic-messages` | `PI_CACHE_RETENTION=long` 为 1h，否则 5m；`model.promptCache` 声明优先 | Anthropic 官方档位 |
| 其他（gpt 中转、未知） | 15m | 实测 15–30m 掉到 6.8% |

这个取值逻辑参考 pi 缓存预热的 TTL 函数（未导出），DeepSeek 门限在长间隔快照实测后改为 3d。实际效果：时间门控主要对 claude 和 gpt 起作用。

放弃过 TTL 自动推断，原因如下：累积统计会被几千个秒级样本主导，TTL 恒被推到最高档；统计检验要求每区间至少 16 个样本，实际凑不够；样本单位错了（一次 run 内的秒级请求不是 TTL 证据，应按"空闲片段"取样）。现在是静态取值，观测只做告警。

## 10. 实测发现

### 10.1 历史数据（42 个会话，2,901 条带 usage 的 assistant 消息）

每回合 prompt 大小：p50 107k、p90 341k、p99 544k、max 688k。首回合基线（系统 + 工具 + 第一条消息）：最小 6.9k、中位 13.8k、最大 21.8k。

五次历史手动压缩的 `tokensBefore` 为 398k / 592k / 481k / 365k / 546k，都在 1M 窗口的 36–59%，默认阈值在 983k，自动阈值从未触发过。压缩后第一次请求 58k–81k：系统加工具约 21k、摘要 4–10k、保留区 25–42k。

命中率（cacheRead / prompt），按相邻请求的间隔：

| 间隔 | claude | deepseek | gpt 中转 |
| --- | --- | --- | --- |
| < 5m | 97.8%（1083） | 99.1%（1047） | 86.9%（425） |
| 5–15m | 78.9%（22） | 99.7%（7） | 64.4%（10） |
| 15–30m | 99.4%（3） | 98.7%（1） | 6.8% |
| 30–60m | 93.1%（6） | 99.1%（3） | 3.2% |
| > 2h | 6.2%（5） | 无样本 | 无样本 |

括号内为样本数。156/2,805 条消息的 usage 全为 0（stopReason 为 error 或 aborted），统计时已剔除。

### 10.2 系统提示中途变更会让缓存整体失效

全数据集共 7 次变更，其中 4 次有后续请求可读：变更的段为 tools / project_context / rules / skills，下一次命中率分别为 0.3%、0.0%、0.0%、4.9%。另外 3 次没有后续请求。这说明前缀比对的严格是必要的，也说明 optimizer 稳定系统提示的价值。

3.26h 那条是唯一的长间隔记录，但低命中是 project_context 变更造成的，不能当作 TTL 到期的证据。

### 10.3 TTL 判断的几次修正

TTL 取值改过四次，每次都有教训：

- 24h → 60m：把前缀破坏误判成过期。恢复会话时插入 `message system` 之类的条目会破坏前缀，此时 cacheRead 不为 0（15,616、10,156），前半段仍命中；真正整体过期时 cacheRead 应接近 0。
- 60m → 12h：按官方口径取保守值，没有本地证据。
- 12h → 24h：有快照之后判据才明确。用 24h 前写入的快照直接发 `-c`：

  | 快照写入 | gap | tokensBefore | cacheRead | 命中 |
  | --- | --- | --- | --- | --- |
  | 10-25 16:01 | 25h04m | 32,956 | 32,768 | 98.3% |
  | 10-25 17:22 | 23h43m | 26,283 | 26,112 | 97.9% |

  两次 cacheWrite 均为 0，未命中的 563–580 token 就是压缩指令本身。DeepSeek 的实际保留期至少 25 小时。这是四次取值中唯一有快照证据的一次。
- 通过修改快照 `at` 字段伪造 30h 间隔再 `-c`，命中 99.4%，但这不能证明缓存活了 30h：服务器端缓存是几秒前写的。

另一条旁证：10-25 12:02 的 native 压缩在 33 小时间隔后仍拿到 cacheRead 73,216，来自 DeepSeek 块级缓存对旧摘要文本的命中。它不能当作 append 命中的证据，但支持长保留。

历史统计只能回答"观测到的最长干净命中"（deepseek 40.8m、claude 47.3m、gpt 中转 10.3m），不能回答"缓存寿命上界"。要进一步校准 claude 与 gpt 的取值，必须用落盘快照逐条比对 system/tools/messages 前导部分是否逐字一致，历史数据缺少当时的 payload，区分不了前缀破坏与缓存过期。

### 10.4 append 路径实测（deepseek-flash）

| 场景 | 结果 |
| --- | --- |
| `/compact -c`，缓存未过期 | 命中 99.6%，摘要首行为 `## Goal` |
| `/compact -nc` | read 0%，走 native |
| 新进程 resume 后立刻 `-c` | 命中 99.3% |
| 删掉快照后 `-c` | `native(no-snapshot)`，warning 级别 |
| 带 `-c` 与 `--model` 指向另一个模型 | 降级 native 并提示 |
| `--model nope/nothing` | 报错并列出候选，`cancel`，无请求 |
| 阈值触发（把 `reserveTokens` 调大强制） | `append(auto)`，命中 99.4%，输出上限 32768 生效 |
| 跨压缩的文件清单 | 第二次压缩后仍在 |
| 死端口下 `-nc`（旧实现，已不再存在的内置回落路径） | `native(-nc\|builtin)`，明细行报 `-` |

另有生产日志中的记录：`append(forced)` 命中 99.6%–99.7%。

### 10.5 `--effort`

| 命令 | 命中 |
| --- | --- |
| `-c --effort low`（会话为 high） | 99.7% |
| `-c --effort high` | 99.4% |
| `-c --effort max` | 18.5% / 13.0% / 17.9% |

low 与 high 互换不影响命中。`max` 三次都恰好停在 cacheRead 15,744，与"压缩后首次请求"的命中量相同，说明请求与最近缓存的前缀从很早就分歧。请求里唯一的差异是 `reasoning_effort` 取值。机制未查明：评审推断分歧点在 system/tools 与消息之间（system 约 30k 字符 + tools 约 35k 字符约等于 15.7k token，量级对得上），DeepSeek 可能对 `max` 走独立分支，都没有直接证据，不据此写额外逻辑。统计行命中率 ≤ 25% 会发 warning，这种情况在 TUI 上能看到。

## 11. 失败模式

按"是否会静默变坏"排序：

1. 前缀不命中但请求成功。几十万 token 按全价计费，没有任何报错，是主要风险。成因：Anthropic 断点移位、亲和请求头缺失、扩展加载顺序错误、`--effort max`。防线只有前缀比对和事后读 usage。
2. `fromHook` 导致后续 pi 自己的压缩丢文件清单。质量静默下降。防线是条目里自行累积，且扩展不再把压缩交回 pi。
3. 检查点内容残缺但标题齐全。标题校验通过，摘要质量下降。没有自动防线。
4. 快照取错（预热或摘要请求）。比对失败，降级后多花一次读取的钱，不静默。
5. 溢出路径走 append。上下文已超窗，必然失败。防线是 `overflow` 直接走 native。
6. `PI_CACHE_RETENTION` 消失。它是 `pi-cache-optimizer` 加载时写入 `process.env` 的，不在 shell 里；换环境或临时禁用 optimizer 都会让它消失，claude 的 TTL 从 1h 缩到 5m，表现只是压缩变贵。

## 12. 未验证与已知代价

未验证：

- `--effort max` 稳定未命中的机制（见 10.5）。
- Anthropic 侧 `onPayload` 抛错的 catch 分支（按 openai-completions 的行为推断，未逐行核对）。
- claude、gpt 中转和本地模型的 append 路径：只有历史请求统计，没有专门的压缩实测。
- `after_provider_response` 是否覆盖扩展自己发起的 `streamSimple`。目前判断不覆盖，这符合需要（压缩请求不应成为快照）。若 pi 改成全覆盖，症状是统计行 MISS。
- 路由型 provider 是否依赖回放的请求头（磁盘快照不存请求头）。
- provider 侧是否对旧工具结果做截断。

已知并接受：

- 本地模型的 KV 在进程重启后丢失，扩展看不出来，会承担一次全量 prefill（代价是时间，不是费用）。
- native 路径不经过 pi 的虚拟模型路由，也不用 pi 的重试设置。当前没有使用虚拟模型。
- 命令名 `/compact` 无法被扩展接管：交互模式的硬编码分支在扩展命令派发之前返回。所以参数通过 `/compact` 后的文本传入。
- 扩展没有写 settings.json 的权限，`reserveTokens` 等只能由用户手改。

## 13. 使用与排查

```
/compact [-c|--cached | -nc|--not-cached] [-m|--model <provider/id>] [-e|--effort <level>] [focus text]
```

开关只从行首连续、未加引号的 token 里识别，遇到第一个非开关 token 或带引号的 token 就停止，剩下全部当摘要侧重。`-c` 强制 append（越过 TTL 猜测，不越过余量），`-nc` 强制 native。

每次压缩向 `~/.pi/agent/compact-cache.log` 追加一行 JSON，记录模式、tag、tokens、间隔、TTL 门限、命中率、快照模型与档位等，超过 64KB 轮转为 `.log.old`。这是排查"为什么没走 append"的主要依据。压缩结束后统计行显示在编辑器上方的 widget 里，下一次 `agent_start` 清空。

注意统计行的"模型"是实际执行摘要的模型，原生路径配置了 `NATIVE_SUMMARY_MODEL` 时与会话模型不同；日志里的 `snapModel` 才是会话模型。

自检：

```
env -u PI_CACHE_RETENTION COMPACT_CACHE_SELFTEST=1 bun compact-cache.ts
```

自检依赖环境变量：`PI_CACHE_RETENTION=long` 时 "a TTL shorter than the margin still gets its full TTL" 一条会失败，因为 `ttlMs` 取的是 `promptCache.long` 而测试只声明了 `short`。这是测试对环境的依赖，不是实现错误；用 `env -u` 去掉该变量后全部通过（本次写文档时核对过）。
