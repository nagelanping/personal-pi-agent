## 中文写作与改写

先执行 `SKILL.md` 的规则。凡是面向人的中文文本都读本文件，并与对应领域的 prompt 合用。本文件处理两类问题：英文句法搬进中文造成的英式中文，以及中文自身的表达要求。

### 语域

默认使用偏书面的语言组织方式：主谓宾清楚，关系词齐全，用词是日常通用词。论文、合同、规范、正式公告等专业场景，按需使用正式书面语和领域术语。两种情况都不改成口语，也不为显得正式而套用复杂句式。

本文件的示例默认用于书面场景。`进行……调整`、`此外`、`该`、`过`、`将于`、`予以` 等书面表达照常使用；改写不得降低原文的书面程度。

### AI 中文的三类常见错误

#### 为显得生动而生造表述

为了显得生动、像人，写出既不简短、也不口语的说法，包括圈内黑话、比喻性动词、自造词和符号压缩。读者要先解码才能理解。

- 判据：换成完整的常规说法后，信息不变，读起来更容易。
- 改法：写出主语和谓词；用关系词代替 `→`、`/`、`+`、`>`（代码、命令、表格除外）；括号只放补充信息，不放主要信息。

示例：

- `foo：常驻的对话运行时。` → `foo 是常驻的对话运行时。`
- `会话：a.ts（…）→ b.ts（…）→ c.ts（…）` → `a.ts 管理所有会话；b.ts 运行单个会话；c.ts 负责构建会话。`
- `配置在 config.ts（环境变量 > config.json > 默认值）` → `配置在 config.ts：环境变量优先于 config.json，其次是默认值。`
- `新的判断标准要带反证：故意改坏，确认测试变红，再恢复。` → `新增判据时要验证测试确实能抓到它：先故意改坏被测代码，确认测试失败，再恢复。`
- `smoke 走真实模型，花钱` → `smoke 使用真实模型，会产生费用`
- `跨层名称唯一要靠这把锁` → `跨层名称唯一由 nameLock 保证`
- `坑` → `注意事项`；`跑测试` → `运行测试`；`杀进程` → `停止进程`；`互相串` → `互相干扰`

#### 为显得正式而套用非中文句式

即英式中文，见下一节“英式中文的常见形态”。

#### 为显得严谨而堆砌防御性表述

规则见 `SKILL.md` 的 Defensive negation and disclaimer boilerplate。

- `代码必须同时能在 Bun 和 Node 下运行` → `代码要同时能在 Bun 和 Node 下运行`。标题或上下文已经表明是约束时，不逐条加“必须”；规范文本中区分 MUST 和 SHOULD 的“必须”保留。
- `测试直接调用 start()` → `测试调用 start()`。“直接”不区分任何对照时删去。
- `TypeScript 直接运行` → `两个运行时原样执行 TypeScript 源码`。“直接”有实际含义时，写出它指什么。
- `EventSource 不能带 Bearer token` → `EventSource 无法设置 Authorization 请求头`。含糊的否定改成准确的事实。

### 英式中文的常见形态

判断标准：中文按自身习惯能说得同样准确时，用中文句法；中文句法无法准确表达时，才保留欧化结构。已经归化的欧化用法照常使用，例如“她/它”的区分、“最……之一”、准确的书面长句。修正对象是英文句法骨架。句子长、语体书面、使用术语，都不构成修改理由。改写后保持原有的书面程度，不改成口语。

每项给出判据、改法和保留条件。例句只调整句法，不增减信息。

#### 名词化与虚义动词

书面文本中，`进行调整`、`作出决定`、`给予支持` 等“虚义动词 + 双音节动词”是正常用法，保留。只处理叠加结构：虚义动词、“对……的”和动名词叠在一起，动作被埋进多层修饰。

- `完成了对方案的讨论` → `对方案进行了讨论`
- `实现了对处理效率的有效提升` → `有效提升了处理效率`
- `团队完成了对系统的稳定性的检查` → `团队对系统稳定性进行了检查`

保留：公文、法律中的固定表述（`进行公示`、`予以受理`）；已成为术语的名词化（`增量编译`、`执行计划生成`）。

#### 抽象后缀与范畴词

“化、性、度”后缀，以及“这一环节、这一过程、……方面”等范畴词，多数可删去或还原为动词。

- `验证这一环节需要前置化` → `需要提前验证`
- `在性能方面有所提升` → `性能有所提升`
- `任务颗粒度过粗` → `任务粒度过粗`

保留：有确切定义的术语（`可扩展性`、`幂等性`、`粒度`、`标准化`）。删后缀前先确认它在该领域是否为术语。

#### “被”字句

英文被动语态常被逐句译成“被”字句。中文多用受事主语句表达被动。

- `这个问题已经被解决了` → `这个问题已经解决了`
- `方案被评审组一致通过` → `评审组一致通过了方案`

保留：表达受损或不如意（`账号被锁定`、`数据被误删`），以及需要点明施事的句子。学术方法部分按学科惯例处理。

#### 介词与连接框架

英文的 when、in、as、based on、through、for 常被直译成句首框架。

- `当模型收到指令时，它会先生成计划` → `模型收到指令后，先生成计划`
- `在昨天的会议上，我们确定了方案` → `我们在昨天的会议上确定了方案`
- `作为一个开源项目，它的代码托管在 GitHub` → `该开源项目的代码托管在 GitHub`
- `基于对日志的分析，我们发现……` → `分析日志后，我们发现……`
- `通过引入缓存来降低延迟` → `引入缓存以降低延迟`
- `对于这个问题而言，关键在于复现` → `这个问题的关键在于复现`

保留：“作为”表示以某种身份行事（`作为负责人，我批准该变更`）；框架承担限定范围的作用，删去后句子会被读成全局断言。

#### 代词回指

英文靠代词回指，中文常靠重复名词。

- `Copilot 和 Cursor 都提供代码补全，前者较保守，后者较激进` → `Copilot 和 Cursor 都提供代码补全。Copilot 较保守，Cursor 较激进。`

保留：学术、公文、法律中的“该”“上述”“其”；先行词明确且唯一时的“它”。

#### 冠词式量词与复数标记

英文冠词 a/an 和复数 -s 被直译为“一个、一种、们”。

- `这是一个很好的方法` → `这个方法很好`
- `我们提供了一种新的缓存策略` → `我们提供了新的缓存策略`
- `各位专家们` → `各位专家`

保留：数量本身有意义（`只出现了一次`）。

#### 长定语

英文后置定语从句被搬到名词前，形成“一个……的……的 X”。

- `我们需要一个能够理解上下文并据此作出决策的 Agent` → `我们需要一个 Agent，它能理解上下文，并据此作出决策。`

判据：名词前的修饰语含两个以上“的”，或包含完整小句。改法：先给名词，再把修饰内容拆为后续分句。

#### 系词判断句

英文 be + 形容词、It is ... that 被译成“是……的”。

- `这一步是非常必要的` → `该步骤十分必要`

保留：说明已发生事件的时间、地点、方式（`他是昨天到的`）；技术属性陈述（`该接口是线程安全的`）。

#### 显性连词

英文要求显性衔接，中文小句可以靠语序或动词表达关系。

- `因为服务器负载过高，所以请求超时了` → `服务器负载过高，导致请求超时`
- `他打开了终端和运行了脚本` → `他打开终端，运行了脚本`

段首或句首的 `然而`、`因此`、`此外`、`与此同时`、`换言之`、`总而言之` 在书面文本中是正常用法。只有连接词表达的关系不存在，或相邻多段机械地都以连接词开头时，才按 `SKILL.md` 的 Mechanical transitions 处理。

- `因此，两组的基线存在差异。` 前文没有给出原因时 → `两组的基线存在差异。`

保留：删去连词后因果、条件或转折会被误读；条件说明、操作步骤、规范文本。

#### 时态标记

英文时态被逐词译成“将会、正在……中”。

- `我们将会在下周发布` → `我们将于下周发布`
- `目前正在处理中` → `正在处理`

保留：“已经”“尚未”等区分完成状态的词，属于受保护内容。

#### 状语后置

英文常把条件、时间状语放在主句之后，中文习惯先交代条件。

- `请求会被拒绝，如果令牌已经过期` → `如果令牌已经过期，请求会被拒绝`

#### 借译短语

| 借译                                | 通行说法               |
| ----------------------------------- | ---------------------- |
| 扮演……的角色（play a role）         | 起……作用，或直接写动作 |
| 具有……的能力（have the ability to） | 能                     |
| 在……的帮助下（with the help of）    | 借助                   |
| 死线（deadline）                    | 截止时间               |

判据：短语回译后恰好对应一个英文固定搭配，且中文有更通行的说法时替换。已通用的词和计算机术语（软件、进程、指针、句柄）不替换。

### 篇章与标点层面的 AI 痕迹

以下各项都有可定位的触发标记，按标记逐句判断。

#### 翻案句式

先设定一个读者并没有的误解，再推翻它。常见写法有 `不是……而是……`、`并非……而是……`、`不在于……而在于……`、`与其说……不如说……`、`表面……实际……`、`看似……实则……`、`不是 A，是 B`、`你以为……其实……`、`回头才发现`、`说到底`、`答案恰恰相反`、`A 不重要，重要的是 B`。字面不同、做的是同一件事时，同样处理。

改法：直接陈述判断，再给依据。改写他人文本时，被否定的一半如果是原文要表达的论点，保留为单独的陈述。

- `真正的壁垒不是技术，而是认知。` → `真正的壁垒是认知。`
- `你以为用户在乎功能多少，其实他们只在乎能不能马上用。` → `用户只关注产品能否立即投入使用。`

保留：读者或原文确实持有该误解，文中也用材料完成了纠正；纠正事实错误（`接口返回的单位是秒，不是毫秒`）。

#### 段首零回指评论

非首段以评论语开头，例如 `听起来`、`看起来`、`更重要的是`、`关键在于`、`问题在于`、`不难看出`、`意味着`，句中却没有 `这`、`那`、`其`、`此` 等回指成分，读者要回到上一段找评论对象。

改法：补回指词，或从上一段取出评论对象写明。`值得注意的是` 属于空洞框架语，删去。

- `听起来像一次普通的功能更新。` → `这听起来像一次普通的功能更新。`
- `问题在于，缓存没有失效机制。` → `这个方案的问题在于缓存没有失效机制。`（“这个方案”取自上一段）

保留：首段；已有回指成分；对话和引文。

#### 提示语冒号与空转引导句

冒号前是 `一句话总结`、`核心是`、`关键在于`、`原因如下`、`结论`、`本质上`、`换句话说` 等提示语。提示语不承载信息时删去，直接写内容；承载信息或承接上文时保留，把冒号改成逗号、句号，或改写成完整句子。

- `一句话总结：这个方案成本太高。` → `该方案成本过高。`
- `原因有两个：交付晚了，预算也超了。` → `原因是交付延期和预算超支。`

正文中一行只宣布下面有列表、以冒号结尾，删去后信息不减时，删去这一行，或写成有内容的陈述。列表项不动。

- `我见过的几种典型场景：` → `以下为笔者遇到过的几种典型场景。`

保留：引出直接引语；小标题、列表项内部、代码和字段中的冒号。句中冒号的用量因作者而异，单处不作为修改理由；同一段中每句都靠冒号分层时才处理。

#### 揭晓式破折号

说明性文本中，用破折号制造停顿、随后给出一个简短答案。

- `答案其实很简单——专注。` → `答案是专注。`

这项修改高度依赖场景。破折号承担强调、补充说明或叙事节奏时保留；改后语气或节奏变差时保留原文。用户提供的风格文档表明作者惯用破折号时，按风格文档处理。

#### 理想化职业人格喻体

把工具、系统或流程比作理想化的人：`像` 或 `相当于` 加 `一位`、`一个`，再加导师、秘书、助手、顾问、管家、审查员、实习生等角色，喻体带 `智慧的`、`永不疲倦的`、`全能的` 等褒义修饰，或后接 `不仅……更……`。

改法：写出它实际做什么。

- `它就像一位智慧的导师，不仅传授结论，更传授看待世界的多元视角。` → `它除了给出结论，也说明看待问题的不同角度。`
- `这相当于为团队配备了一个永不疲倦、秒级响应的初级审查员。` → `它可以持续运行，在秒级内响应，能承担初级审查工作。`

改写时，不因为一句话是比喻就删除。比喻提供了正文没有的理解时保留；只是把已讲清的机制换个说法重复时，按语域要求删去。文学体裁按原有风格判断。

#### 起手语

`说白了`、`说穿了`、`先说结论` 删去，直接给出判断。

- `说白了，这个项目没有足够的预算。` → `这个项目预算不足。`

#### 小标题通篇编号

连续三个以上小标题以 `一、`、`二、`、`三、` 或 `第一`、`第二` 开头。

改法：删去编号，标题文字、顺序和层级不变。

保留：论文、公文、法规、合同等按体例编号的文本；编号被正文引用（`见第三条`）；内容按步骤或时间组织；Markdown 有序列表。

#### 相邻句同一句法骨架

相邻两句以上，逗号数、成分顺序和长度都接近，例如连续出现“主语＋动词＋宾语，＋补充说明”。

改法：调整其中一句的结构，可以合并、拆分或换语序。只改句内结构，不增删信息，不调整段落顺序。

- `新功能上线后，用户反馈良好。团队的开发效率提升明显。下一步的优化方向已经确定。` → `新功能上线后用户反馈良好，团队开发效率明显提升。下一步的优化方向已经确定。`

一段中并列三个以上平级案例、说明的是同一件事时，可以合并同类项，或把次要案例压缩为半句。信息不删，只调整主次。叙事推进不算平级案例。

保留：操作步骤、并列条款、对话与引语、文学体裁中有意的排比。

### 不作为修改理由

以下特征常被当作 AI 痕迹，但人类写作中同样常见或更常见，不据此修改：

- 句长、段长不够参差。不为制造节奏而调整句长或拆分段落。
- 单字虚词（`就`、`很`、`了`）和口语连接词偏少。不为显得像人而补虚词或口语。
- 反复写全称、少用代词。
- 被动句、名词化和长句本身。只处理本文件列出的具体形态。
- 正文中的 `首先……其次……最后` 和句中的 `第一，`。
- 句内同构排比（`提升效率，降低成本，优化体验`）。跨段反复出现的三点结构按 Forced triads 处理。
- 正文问句和问句小标题。紧接着自答、用来制造揭晓效果的设问，按翻案句式的标准改为直接陈述。

### 中文表达要求

#### 动词承担句子

句子的主要动作用实义动词，或“虚义动词 + 双音节动词”的书面搭配表达。动作被“对……的”等多层修饰埋没时，找出真正的动作。

#### 具体信息只来自材料

起草时，用作者提供的数字、对象和动作代替抽象判断；材料中没有，就保留抽象说法或向作者确认。改写时，具体信息只能来自原文和上下文。不为显得具体而补数字、场景、经历或原因。

- 原文：`这带来了深远的影响。`
- 错误改法：`三个月后，团队里没人再手写单测了。`
- 正确处理：保留原句，提示作者补充具体影响。

原文用数据支撑结论时，结论和数据都保留，不用数据替换结论。

- 保留：`新系统提升了处理效率，处理时间由两小时缩短至四十分钟。`

#### 长句与停顿

长句本身没有问题。连续约 30 字没有停顿、读者难以断句时，先在语义停顿处补逗号；一句中塞入几件可以各自独立的事时，才拆句。不为缩短句子而改成口语。

- `验证要在代码生成的同时就地进行而不是等到整个模块写完再回头逐行核对` → `验证要在代码生成的同时就地进行，而不是等到整个模块写完再回头逐行核对。`

#### 不复述已说过的内容

段末不复述本段结论（`综上所述`、`由此可见`、`换言之`）。相邻两句表达同一意思时合为一句，判据是合并后信息不减少。同一概念的术语照常重复，不为避免重复而换同义词。

以 `这意味着`、`这表明`、`这说明` 开头的句子，若只是用口头化的说法重复前句，合为“结论 + 依据”的一句，并统一为书面表达；给出前句推不出的新结论时保留。

- `平均延迟从 200 ms 降到 80 ms。这意味着接口响应变快了。` → `接口响应速度提升，平均延迟由 200 ms 降至 80 ms。`

#### 词语搭配

动词、形容词要与主语和宾语搭配。为追求力度选用不搭配的词属于用词错误。

- `这一趋势正在塌陷` → 按原意改为 `减弱` 或 `逆转`；原意不明时询问作者。

#### 不自造词

能用现成词表达时不造新词。确需新词时，一篇最多一个，在首次出现的同一段解释，不放进标题。领域内已确立的术语（`技术债`、`上下文工程`）不算自造词。“XX 心智、XX 抓手、XX 势能、XX 打法”等“业务词 + 抽象后缀”组合按自造词处理。

### 标点

- 中文正文使用全角标点。代码、命令、英文原文、数字（`1,000`、`3.14`）、文件名和 URL 保持半角。
- 检查命令，命中后人工排除代码块：

```bash
grep -nP '\p{Han}[,.;:](?!\d)|[,;:]\p{Han}' FILE.md
```

- 破折号、分号和加粗的限制见 `SKILL.md` 的 Punctuation tics。

### 不改的情况

- 改后读者理解不变、只换了说法时，不改。
- 文体需要的客套和正式语气保留：通知、感谢信、客服回复、对外公告。
- 法律、合同、规范文本只做明显的句法修正；可能改变权利义务的措辞不动。
- 原句有两种以上读法、上下文无法确定时，不替作者选择；保守修改并说明歧义。

### 最终检查

- 每处修改都能对应本文件或 `SKILL.md` 的一项规则。
- 每处修改都能指出触发标记，没有依据“不作为修改理由”中的特征改动文字。
- 改写中的每条信息都能在原文或上下文找到出处。
- 术语、数字、否定、情态、因果方向与原文一致。
- 书面程度没有降为口语。
